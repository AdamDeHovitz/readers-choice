# Verification: feat: MCP server for AI apps, with its own OAuth 2.1 authorization server

## Change

AI apps can connect to a user's account over OAuth 2.1 and call operations as MCP tools at `/api/mcp`. A user approves on a consent screen, where writes are allowed by default and admin powers are off by default, and can disconnect in Settings. Separately, the existing auth gains web sign-in rate limits, revocation on Google linking, a derived mobile token key, and a stricter `callbackUrl` check.

### Authorization request errors (no open redirect)

As bob, with a registered client and a malformed request (`response_type=token`): `200`, no `Location` header. The page shows "Can't connect this app", and a link "Back to claude.ai" points to `https://claude.ai/api/mcp/auth_callback?error=unsupported_response_type&…&state=s&iss=http%3A%2F%2Flocalhost%3A3200`. Before this fix the same request returned a `307` to that URL. The error codes, checked before the change from redirect to link:

- missing PKCE → `invalid_request`
- `plain` method → `invalid_request`
- foreign `resource` → `invalid_target`
- repeated `state` → `invalid_request`

### Audit fixes, live

- **Consent copy**: "Approving sends access to an app on this device. Address: http://127.0.0.1:7777/cb. The app chose the name "Claude" itself, so check the address."
- **Settings host**: a client registered as "Claude" with `[claude.ai…, 127.0.0.1…]` that got access via 127.0.0.1 is listed as `Claude · 127.0.0.1:7777`, not `claude.ai`.
- **Refresh replay**: first refresh 200; immediate replay of the old token 400 `invalid_grant`; then the newest token 400 `invalid_grant`, so the grant was revoked.
- **`X-Forwarded-Host: evil.example`**: the issuer stayed `http://localhost:3200` with `cache-control: no-store`, and the challenge's `resource_metadata` stayed on localhost.
- **Web sign-in rate limit**: after 11 wrong passwords for carol in the browser, the correct password stayed on `/login`. Mobile sign-in for carol then returned `429 rate_limited`, showing the shared email bucket.
- **Settings Disconnect**: clicking Disconnect on a connection made its access token return `401` on the next MCP call. The `oauth_grants` row showed `revoked = t`.

All test data was deleted afterwards: the OAuth rows, the test themes, `rate_limits`, and the mobile sessions created during testing.

## Not verified

- **The migration from scratch**: I didn't run `npm run db:reset`, because the local stack is shared with other sessions. I applied the migration's SQL directly, then the later `redirect_uri` column with the same definition as the file, and regenerated types. CI's E2E (fresh stack from migrations, plus the types check) and Migration compat cover this.
- **Google sign-in changes** (revocation on linking, a different Google account refused, `email_verified` on web): unit tests only, since Google sign-in doesn't work locally or on previews.
- **Anything on Vercel**: whether `Host` is the requested domain (the code now ignores `X-Forwarded-Host`), whether `AUTH_SECRET` differs between preview and production, and a real Claude.ai connection. All of these need a deployed URL. Preview URLs are behind SSO, so Claude can't reach them; the first real test is production.
- **The mobile app after the access-token key change**: not run. The app's existing retry-after-refresh path should absorb the one 401.
- **A rebinding or slow-drip metadata server**: the DNS check at connect time and the 5-second deadline are covered by reading the code and by unit tests, not by a hostile server.
- **Real AI hosts' handling of member-written text**: prompt injection was not exercised against a model.

## Harness gaps

- **Ports**: 3000 and 3100 were held by other sessions, so the app ran on 3200. Playwright's `page.route` doesn't catch a redirect into an intercepted URL, so redirect responses had to be checked with `page.request.get(…, { maxRedirects: 0 })`.
- **No local OAuth/MCP harness**: the end-to-end scripts (DCR → login → consent → token → MCP) live in a scratch directory. An `apps/web/e2e` spec for the OAuth flow would guard it, and is worth adding.
- **Rate-limit state leaks between runs**: it's shared with the stack, so one test's lockout broke another until `rate_limits` was cleared.
