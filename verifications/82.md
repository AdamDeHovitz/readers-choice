# Verification: feat: mobile sign-in (password + Google) with rotating refresh tokens and a bearer viewer

## Change

The mobile app can sign in with email/password or a Google ID token at `POST /api/v1/auth/*`, refresh and sign out, and call any `/api/v1` operation with a bearer access token. Sessions live in a new `mobile_sessions` table (hashed refresh tokens, rotation, replay revocation, 90-day idle expiry). Web sign-in is unchanged.

## Checks

- `npm run db:reset`: the migration applies cleanly on top of every existing migration and the seed. `npm run db:types` regenerated `apps/web/server/database.types.ts` (+45 lines, the new table only).
- `npm run lint`: clean
- `npm run typecheck`: clean
- `npm run test:run`: 40 files, 418 passed (main: 36 files, 396). New: `server/mobile-sessions.test.ts` (7), `server/google-id-token.test.ts` (4), `app/_operations/auth-http.test.ts` (8), `server/viewer.test.ts` (3).
- `npm run build` (dummy env): compiled; routes `ƒ /api/v1/auth/{google,password,refresh,sign-out}` and `ƒ /api/v1/[operation]`.
- `PORT=3200 npm run test:e2e`: 14 passed (web cookie sign-in and pages unaffected).

## Not verified

- **Google sign-in with a real Google ID token.** There's no iOS client ID yet, and native sign-in needs the app. Verification is covered by unit tests with a locally generated RS256 key set (audience, issuer, expiry, verified email, wrong signing key). The live endpoint was only checked refusing while unconfigured.
- Production-like rate limiting: the `consume_rate_limit` function is the one registration already uses; not hammered live.
- **Revocation latency.** A revoked session's access token keeps working until it expires (≤15 minutes), by design. Not exercised live.

## Harness gaps

- `npm run db:reset` wipes the one local database every worktree shares, and a new migration requires it. Nothing else was running against it this time.
